# Findings draft part 12 — secrets in version control, settings exposure, Flutter bootstrap

No secret value is reproduced anywhere in this report; comparisons below were done in memory and only booleans were printed.

## SEC-1 [CRITICAL, CONFIRMED in git; production equivalence NOT verified]
Credentials were committed to the repository and the commits are on the GitHub remote.
- Evidence (all from `git log` / `git show`, names only):
  - `0d423333` ("Production release commit without heavy binaries", 2026-09-04) added `functions/backend/.env` and `functions/backend/serviceAccountKey.json` (+ a root `serviceAccountKey.json`).
  - `70130744` added `admin/frontend/backend/.env` and `admin/frontend/backend/serviceAccountKey.json`.
  - `4ffc19ee` added `admin/backend/.env`.
  - `523258f9` ("untrack node_modules, .env files and service-account keys") removed them from the tree but **not from history**.
  - `git branch -a --contains 0d423333` lists `origin/main` and `origin/fix/deploy-readiness`, i.e. the secrets are in the pushed history of `https://github.com/youpeak24/youpeak`. Repository visibility (public/private) could not be checked (`gh` is not installed here): **BLOCKED — confirm on GitHub; treat as exposed regardless, since any collaborator, CI cache or fork holds a copy.**
  - Variables that carried a **value** in the committed `.env` files (checked in all three revisions, booleans only): `secretKey`, `JWT_SECRET`, `MONGODB_CONNECTION_STRING`, plus `PORT`, `appName`, `EMAIL`, `baseURL` and (older files) `CLOUDFLARE_R2_BUCKET`. The Cloudflare account id, API token, R2 access/secret keys and public domain were **blank** in every committed revision, so no Cloudflare credential was exposed through `.env` (they live in the settings document / Vercel env).
  - Equality check against the current local `functions/backend/.env`: `JWT_SECRET`, `secretKey` and `MONGODB_CONNECTION_STRING` in the committed revision are **identical** to the values in the working copy; the Firebase Admin service-account `private_key_id` and `project_id` in the committed `serviceAccountKey.json` are **identical** to the local file the backend loads.
- Impact: whoever can read the history can (a) sign admin JWTs — the admin login/guard uses `JWT_SECRET`, and admin `_id`s are in the tracked `DB/admins.json` (2 seed admins: SUPER_ADMIN and AGENCY_ADMIN), so a valid SUPER_ADMIN token could be forged if production still uses this secret; (b) act as the Firebase Admin SDK (read/write all Firestore, Auth, Storage, mint custom tokens for any user id — the user ids are guessable `Date.now()` values, P-02); (c) use the database connection string. `secretKey` (shared app key) is public by design, so its leak adds nothing.
- Whether production uses the same values: **not verified** (reading deployed environment variables was out of scope). DEPLOYMENT.md states that a super-admin password and JWT secret fragments were previously committed.
- Fix (do not do silently): rotate the Firebase service-account key, `JWT_SECRET` and the database credentials (and review Cloudflare tokens as a precaution); revoke the old key in Google Cloud; rewrite history (`git filter-repo`) or archive the repository; add a pre-commit/CI secret scan (gitleaks); keep `.env`/keys only in Vercel/Secret Manager. Verification: `git log --all -- '*serviceAccountKey.json' '*.env'` empty after rewrite; old key rejected by Google; old JWT rejected by `/admin/...`.
- Also tracked today: `youpeak/android/app/google-services.json` and `youpeak/ios/Runner/GoogleService-Info.plist` (Firebase client config — public by design, not a secret) and `.env.example`.

## SET-1 [Medium] Client settings sanitiser is a deny-list
`controllers/client/setting.controller.js:19-72` builds the response to the unauthenticated-by-user (shared-key-only) `GET client/setting` by copying the whole settings document and deleting ~60 named keys (`SENSITIVE_SETTING_KEYS`). Any secret-bearing field that is added to the settings document later, or named differently (e.g. `razorKeySecret`, `smtpPassword`, `resendKey`), is published to every visitor, because the shared key is compiled into public bundles. The Flutter app even has getters that read `stripeSecretKey`/`razorSecretKey` from this response (`app_string.dart:526,536`) — they resolve to empty today only because of the deny-list. Fix: build the response from an explicit allow-list of public fields. Test: add a fake `fooSecret` to the settings doc in the emulator and assert it is absent. (The deny-list as written was checked and covers the gateway, storage, Firebase-admin and JWT fields I could find in the code; it is not proven complete against the production document, which I was not permitted to read.)

## FL-15 [Medium] Third-party credentials shipped to every client
- `Zego appSign` is returned to all clients through the settings response (`zegoAppSignIn`) and used in `createEngineWithProfile` (`main.dart:480`). Zego treats the AppSign as a credential; anyone can extract it and create live-stream rooms billed to the project. Use token authentication (server-issued) instead.
- `Stripe.publishableKey = AppStrings.stripeTestPublicKey` (`main.dart:493`) — the value comes from settings and is a test-mode key (known from earlier probing); Stripe is not used by any working path (FL-1).
- Firebase Web/Android/iOS API keys are in `firebase_options.dart` (public by design; restrict them by HTTP referrer / package name in Google Cloud and enable App Check — not verifiable from the repository, **BLOCKED: console access**).

## FL-16 [Info] Bootstrap observations (`main.dart`)
- Crashlytics, Branch, AdMob, notifications, Zego, Stripe are skipped on web (correct). `FlutterError.onError`/`PlatformDispatcher.onError` are set only on mobile, so web has no error reporting at all — a production web crash is invisible.
- A 5-second `Timer.periodic` runs `InternetAddress.lookup('google.com')` on mobile for the whole app lifetime (battery, and a false "no internet" dialog in networks where google.com is blocked even though YouPeak is reachable); on web it only reads the connectivity state, so a browser that is "online" but cannot reach `api.youpeak.app` shows no offline UI (the API client reports `NETWORK_ERROR` per call instead).
- The text scaler is forced to 0.8 on every non-iOS platform including the web build (accessibility: system/browser text size is ignored and text is 20 % smaller than designed — WCAG 1.4.4). Confirmed in `main.dart:399`.
- `stripeInit`/`onConnectInternet` only run when `CustomCheckInternet.isConnect`; settings (`AdminSettingsApi.callApi`) are fetched inside `onConnectInternet`, so a first cold start while offline leaves `AdminSettingsApi.adminSettingsModel == null` and every getter that reads it returns defaults/empty (`appId` → 0) until reconnect.

## FL-17 [Medium, requirement conflict] Membership/activation flow depends on a portal that returns 404
`MembershipPortal.open` and `ActivationLockView` send the user to `membershipPortalUrl` (default `https://youpeak.in`, DEP-5). The Activation lock screen has `PopScope(canPop:false)`; if an admin ever sets `joiningFeeInr > 0` (or an account is flagged `MEMBERSHIP_PAYMENT_PENDING`) the only exits are the dead portal, "check again" or "use a different account". The `uid` of the logged-in user is appended to the URL as a plain query parameter (`uid=<id>`), so the portal would have to trust a user-supplied id to credit a membership — design risk for the missing portal: it must bind payment to an authenticated session, not to the `uid` parameter.
