# Findings draft part 16 — channel identity, mobile build/store configuration, documentation drift

## ID-1 [High, CONFIRMED on emulator] Two incompatible meanings of `channelId` — channel pages break for channels created by a first upload
- Evidence: `audit-tests/suites/09-playlists.cjs` ID-01..ID-04 (logs/audit-09-playlists.txt).
  - `client/user/update` (the app's "Create channel" call, `create_channel_api.dart`) sets `channelId = <owner's userId>` (`user.controller.js:181-183`, with a comment saying the whole codebase treats channelId as the owner's user id).
  - `client/video/createVideo` creates the channel on a user's first upload (`!user.isChannel`) with `user.channelId = uuid.v4()` (`video.controller.js:435`); the Flutter upload flow supports this (it sends `fullName`, `descriptionOfChannel`).
  - Channel endpoints then resolve the channel by user id: `detailsOfChannel` → `db.findById("users", channelId)`, `db.find("videos", { userId: channelId })` (`user.controller.js:266-270`); `videosOfChannel` → `{ userId: channelId }` (324); `playListsOfChannel` → `{ userId: channelId }` (343).
  - Result on the emulator: a channel whose `channelId` is a uuid → `detailsOfChannel` answers **"Channel not found."** (ID-01), `videosOfChannel` returns 0 videos although the channel has one (ID-03), `playListsOfChannel` returns 0 playlists (PL-02); the control channel whose id equals the user id works (ID-02). Subscribing to the uuid channel succeeds (ID-04), so the subscriber list and the channel page disagree.
- Impact: every creator who started by uploading (rather than pressing "Create channel" first) has a channel page, "My channel" tab, playlists and channel video list that never load; viewers who follow a video's channel link get "Channel not found". Feed rows, subscriptions and revenue use the video's `channelId`, so they keep working, which hides the problem.
- Fix: pick one definition (recommended: `channelId = userId` everywhere, remove `uuid.v4()`), migrate existing uuid channels, and resolve channel pages by `channelId` field instead of the user-document id. Tests: ID-01/ID-03/PL-02 already encode the expectation.
- Related inconsistencies in the same handlers: `videosOfChannel` and `playListsOfChannel` treat `start` as an array offset while `detailsOfChannel` and the app use a 1-based page (PL-03).

## MOB — Android / iOS build and store readiness [S]
- MOB-1 [High for release] Both mobile manifests ship Google's **sample/test AdMob application id** (`AndroidManifest.xml`: `com.google.android.gms.ads.APPLICATION_ID = ca-app-pub-3940256099942544~3347511713`; `ios/Runner/Info.plist` `GADApplicationIdentifier` the same). Real ad-unit ids are delivered from the admin "Advertise" settings, but the SDK is initialised with the test app id, so revenue/ads can fail to serve or be attributed to no account and Play/AdMob policy treats test ids in production builds as a violation. Rewarded-ad earning (Tasker tasks) depends on the ads loading.
- MOB-2 [Medium] `android:usesCleartextTraffic="true"` — the app may talk plain HTTP; the API and CDN are HTTPS, so there is no functional need; it widens interception risk on public Wi-Fi.
- MOB-3 [Medium, App Store] iOS `Info.plist` has placeholder permission texts: `NSCameraUsageDescription = "$(PRODUCT_NAME) camera description."`, `NSSpeechRecognitionUsageDescription = "My description about why I need this capability"` (a speech-recognition capability the app does not appear to use); no `NSUserTrackingUsageDescription` and no `SKAdNetworkItems` although AdMob is integrated (ATT/attribution prompts missing); `aps-environment` is `development` in `Runner.entitlements`; iOS bundle id is the template `com.live.metube` (Android: `com.YouPeak.Live1`). These typically cause App Review rejection (guidelines 5.1.1, 2.1).
- MOB-4 [Low] Version drift: `pubspec.yaml` `1.0.0+1`; Android `build.gradle` hard-codes `versionCode 2 / versionName "1.1.2"` (overrides pubspec), iOS takes pubspec → the two stores would ship different versions of the same code.
- MOB-5 [Medium, process] `build.gradle` signs the **release** variant with the debug key when `key.properties` is absent (`signingConfig keystorePropertiesFile.exists() ? release : debug`) — a CI/dev machine without the keystore silently produces a debug-signed "release" that the Play Store rejects or that cannot update an existing install. `firebaseCrashlytics.mappingFileUploadEnabled false` and `shrinkResources false` with `minifyEnabled true`: obfuscated release crashes will not be symbolicated.
- MOB-6 [Info/compliance] Permissions `READ_MEDIA_VIDEO` / `READ_MEDIA_IMAGES` need the Play "Photo and Video Permissions" declaration; `com.android.vending.BILLING` is declared but the in-app purchase success path is empty (FL-1). `allowBackup` is not set (default allows backup of app data; local storage holds only ids/flags — see below).
- MOB-7 [Info] Leftover template identifiers: Branch test host `lv0x1.app.link`/`lv0x1-alternate.app.link` with `autoVerify=true`, a Branch **live** key in the manifest (identifier, public by design), commented permission blocks.
- MOB-8 [Info, GOOD] Local storage (`GetStorage`/web localStorage) keeps only ids and flags (`loginUserId`, `channelId`, `deviceId`, `fcmToken`, settings); passwords/tokens are not stored by the app (Firebase Auth holds the session); logout erases storage, signs out of Firebase and deletes downloads. `Database.loginType` is declared `int` but read as `localStorage.read("loginType")` (null before first login) → a `TypeError` in the logout path if no login type was ever stored.

## DOC — documentation and release-process drift [S]
- DOC-1 [Medium] `HANDOVER.md` (and `DEPLOYMENT.md` §1) state that every previously committed secret must be rotated and that a history rewrite is "optional". Nothing in the repository proves that this was done, and my comparison (SEC-1) shows the current local `JWT_SECRET`, shared `secretKey`, database connection string and service-account key id are identical to the values committed in history. Treat rotation as **not done until a person confirms it** in the provider consoles.
- DOC-2 [Low] `HANDOVER.md` says the branch is "not pushed" and that changes were "smoke-tested against the live Firestore project `youpeak-9ff65`"; `origin/fix/deploy-readiness` exists today, and the repository now contains an emulator harness that refuses live Firebase (`tests/emulator/harness.cjs`, `server.js` guard). The document also states `/admin/grievance/list` and payment reconcile as the operating path, but the admin UI has no screens for them (AFE-17).
- DOC-3 [Info] `scripts/build-consumer-web.ps1` is a sound release step: refuses private keys/JSON as the client key, enforces an HTTPS API origin, writes the define file under `.dart_tool` and deletes it afterwards. `youpeak/web/vercel.json` proxies `/.well-known/assetlinks.json` and the AASA to the API (`https://api.youpeak.app/...`), which is why the iOS file is the API's empty default (DL-1).

## METHOD note — contract check
`contract-check.cjs` compares query/body parameter names that the Flutter API files send with what the matching backend handler reads. It is a **weak regex heuristic** (it misses literal values such as `type=all` and matches handlers by function name), so its 21 candidates were used only for triage: the ones I verified by reading both sides were the home feed (`type` is sent — false positive), `client/user/update` (works, reads body), and the channel/playlist mismatches that became ID-1/PL-02/PL-03. No claim in this report relies on the heuristic alone.
