# Findings draft part 11 — Flutter consumer app (read so far: core/security, network, payment, deep_link, rewards, payout, coins convert, watch_tracking, auth flows, upload)

## Corrections to earlier drafts
- **FL-3 is withdrawn/narrowed.** Earlier I wrote that the legacy exploitable endpoints (PAY-1..3, WH-1) are not used by the shipped app. That was only true for `createCoinPlanHistory` (the app's `PurchaseCoinPlanApi` sends no payment proof). Two other legacy endpoints **are called by the shipped app**: `client/withdrawalRequest/coinToAmountConverter` (FL-4) and `client/watchHistory/createWatchHistory` (FL-5). Their defects (PAY-4, WH-1) are therefore reachable by ordinary use, not only by a crafted client.

## Money paths used by the shipped app
- FL-4 [High, money — confirms PAY-4 is live] The Convert-coins screen (`features/coins/api/convert_coin_api.dart`) calls **`GET client/withdrawalRequest/coinToAmountConverter?userId=…&coin=…`**: a state-changing **GET** with the user id and amount in the URL (cached/prefetched/logged by proxies and CDNs; replayable from a browser address bar or a link). Server side the conversion does not distinguish earned from purchased coins (PAY-4), so coins bought with money become withdrawable ₹. The preview divides by `minCoinForCashOut ?? 1` (`convert_coin_controller.dart:61`): if the settings call has not returned, the screen shows 1 coin = ₹1 (100× overstated). After success it stores a local notification titled "Withdrawal Requested — Successfully converted N coins to cash" although no withdrawal was requested (conversion only).
- FL-5 [High, money — confirms WH-1 is live and adds a new client-trust issue] Every normal video / Bite screen calls `POST client/watchHistory/createWatchHistory?userId&videoId&videoUserId&videoChannelId&currentWatchTime=<position.inSeconds>` (`normal_video_details_controller.dart:345`, `shorts_video_details_view.dart:116`, `nav_shorts_details_view.dart:259`, `preview_shorts_video.dart:470`) once the player position passes 40 % of the video. Consequences, all confirmed by reading both sides:
  1. the value sent is the **playhead position**, not elapsed play time (a viewer who seeks to the end "watched" 100 %); the parameter is named `watchTimeInMinute` but carries seconds;
  2. the server credits the **creator** `earningPerHour × time` against `video.videoTime`, which is the duration the **creator typed in at upload** (UP-1), capped only by that claimed duration;
  3. the history row is never created (`updateOne … {upsert:true}` is ignored by the shim), so `existingHistory` is always empty and each repeat call credits the creator again (WH-1: 5 calls = ₹10 for one 1-hour video, emulator-proven);
  4. none of this is tied to the secure heartbeat ledger (which does require real foreground, unmuted playback) — the two systems pay independently, so a creator account plus a second account can mint creator earnings without any watching. Creator earnings are withdrawable ₹ (`totalWithdrawableAmount`).
- UP-1 [High] `videoTime` (duration) is supplied by the client in `createVideo` (`video.controller.js:505`, from `upload_video_api.dart:56`) and never verified against R2/Stream metadata. It is used for (a) the Bites length limit (`durationOfShorts`, line 353 — a 10-minute clip can be declared 10 s), (b) the creator-earning cap and 40 % threshold (FL-5), (c) the "finished" 90 % flag in playback sessions. Fix: read duration from Stream (`/stream/webhook` readyToStream) or ffprobe at upload completion, ignore the client value.
- FL-6 [Medium] Payment recovery: `PaymentApi.verify` returns `{status:false,"Something went wrong."}` for any non-200 or network failure. Combined with DEP-4 (no Razorpay webhook secret is configured in production, so webhooks cannot fulfil) a user who is charged and then loses connectivity/closes the tab before `verify` returns is never credited automatically, sees a generic error, and the app keeps no pending-order record to retry. There is no admin screen to reconcile (AFE-17). 4xx messages from the server (e.g. `ORDER_NOT_FOUND`) are discarded.
- FL-7 [Low] Rewarded-ad flow: if no ad is loaded `GoogleRewardAd.showAd` silently does nothing (debug print only) — the user taps Play and nothing happens; the claim is sent only when `onUserEarnedReward` fired (good) but is still self-reported (AF-2). The inter-ad cooldown and progress live in local storage (`Database.nextAdTaskTime`, wall-clock subtraction); clearing storage resets the timer client-side (server enforces its own daily cap and gap, per RW suite).
- FL-8 [Medium] Daily check-in picks "today" with `DateTime.now().day == CustomGetCurrentWeekDate.onGet()[index].day` (device local time) while the reward engine uses the IST business day. A user whose phone is in another zone, or whose clock is wrong, sees the wrong day highlighted/enabled; `index` loops on `day` equality (two weeks cannot collide, but month rollover week with equal day numbers can mis-select). Server remains authoritative (`coinsEarned`), so impact is a confusing UI and a check-in showing as done/undone incorrectly.

## Security / privacy (client)
- FL-9 [Medium] `AppSettings.showLog` is `true == true ? log(text) : null` — logging cannot be switched off in release. Login, sign-up, OTP, set-password and payment responses are logged in full (`login_api.dart:23`, `sign_up_api.dart:47`, `payment_api.dart:39/67`); the sign-up/login response carries `firebaseCustomToken` (a credential that signs in as the user) and the user document. On Android/iOS release builds `dart:developer.log` is not visible to users, but 56 plain `print(...)` calls remain (e.g. `profile_view.dart:52` prints the user id) which do reach the browser console on the web build. **Not confirmed on the deployed web bundle** (needs a browser console capture; `log()` behaviour on dart2js release not verified). Fix: gate on `kDebugMode`, never log bodies of auth/payment calls.
- FL-10 [Medium] Deep links: `DeepLinkServices` accepts `videoUrl` and `id` from any `youpeak.app/share?...` or custom-scheme link and `NormalVideoDetailsView(videoId: id, videoUrl: videoUrl)` plays `videoUrl` when no cached URL exists for that id (`normal_video_details_controller.dart:383-392`, `ConvertToNetwork.convert(videoUrl)`), while the watch ledger and creator crediting attribute the playback to `videoId`. A crafted link can therefore make the app stream an arbitrary https URL under a real video's identity (content spoofing / phishing inside the app; watch time credited to one video while another is shown). Fix: resolve the media URL only from `getVideoDetail(videoId)`; ignore link-supplied URLs.
- FL-11 [Low] `ReferralLink.remember` stores any 6–12 alphanumeric path segment as a pending referral code, and `https://youpeak.app/<anything>` such as `/ABCDEF` is treated as a code unless in a small reserved list (`privacy`, `terms`, `download`, … but not `about`, `help`, `contact`, `pricing`, `admin`, `api`). Referral attribution then depends on the server validating it (RF suite).
- FL-12 [Info, GOOD] `AppApiClient` (`core/network/app_api_client.dart`): bounded 15 s timeouts, one retry with a refreshed token on `AUTH_INVALID`, structured `ApiException` codes, no body logging. `SecurityService` fails open when attestation cannot reach the server but local checks are clean (documented; reward endpoints refuse unattested devices server-side, per AF-1). Web sends no device claims and relies on the server (`WEB_PLATFORM`). Cadence-based bot detection (≥6 actions with σ<120 ms) is trivially evaded by jitter but only a client hint.
- FL-13 [Low] `UploadVideoController.onDeleteDirectory` deletes the whole application temporary directory (`getTemporaryDirectory().delete(recursive:true)`) after each upload, including caches belonging to other plugins/downloads running at the same time. `AppSettings.isUploading` is not reset on the early failure branch before the thumbnail step when the internet check fails (the flag is only set after the check, so fine), but a failed `UploadVideoApi` shows only a generic notification "Upload Failed !!" with no reason (server messages such as `UPLOAD_INCOMPLETE`, "blocked by admin" and channel-name collisions are dropped).
- FL-14 [Low] Auth: Google flow ends the Firebase session when the backend refuses (good), but the email/password sign-in path posts the plaintext password to `client/user/login` (TLS only) and the backend has no throttling (P-04). Phone login relies entirely on Firebase quota (`too-many-requests` is mapped to a friendly message).
