# Findings draft part 15 — remaining backend controllers (playlists, live, settings forms, platform behaviour)

Evidence: [E] emulator run `audit-tests/suites/09-playlists.cjs` (logs/audit-09-playlists.txt); [S] static read.

## Playlists [E]
- PL-01 [High, CONFIRMED, shim `$in` drop — same root cause as D-01] `POST client/playlist/newPlayList` answers "One or more videos not found!" for a single, existing, active video as soon as the platform has more active videos than the number selected. The handler validates with `Video.countDocuments({ _id: { $in: videoIds }, isActive: true })` and compares to `videoIds.length`; the Firestore shim drops the `$in` operator, so the count is the total number of active videos (3 in the fixture, thousands in production). A user can therefore create a playlist only when the platform has exactly as many active videos as they selected. `updatePlayList` (type "add") has the same check (`Video.find({ _id: { $in } })` → length mismatch) and fails the same way.
- PL-02 [Medium, CONFIRMED] The channel "Playlists" tab always renders empty: the app calls `GET client/user/playListsOfChannel?channelId=<Database.channelId>` with the channel **uuid** (`channel_playlist_api.dart:20`, `get_play_list_controller.dart:50`), but the handler filters `playLists` by `userId == channelId` (`user.controller.js:343`) and compares `req.appUserId` with `channelId` for private playlists. A channel uuid never equals a user id (they differ: `user.channelId = uuid.v4()`), so the list is empty for owners and visitors alike (fixture: 3 public playlists → total 0).
- PL-03 [Low, CONFIRMED] The same handler uses `start` as an array offset (`playlists.slice(Number(start), Number(start)+Number(limit))`) while the app sends a 1-based page number (`startPagination += 1` → 1, 2, 3 …). Page 1 skips the first playlist, page 2 skips the first two, so entries are lost/duplicated across pages (fixture: `start=1&limit=2` returned items 2–3, not 1–2).

## Reward configuration sources [S]
- CU-4 / RW-2 [Medium] There are **three independent definitions** of "coins for watching an ad": (1) the admin form "Ads Coin Reward" (`AdRewardCoin` rows: label, interval, coins, shown per row to the app by `client/adRewardCoin`), (2) `settings.adRewardCoins`, a single number that the engine actually pays and that `adRewardCoin.controoler.js:13-27` overwrites with **whichever row was saved last** (so editing row 3 changes what rows 1–5 pay), and (3) `system_configs/tasker_tiers.rewards.adCoins` (25 by default), which is what the Tasker dashboard / V9 rules refer to. The app lists "+N coins" per ad slot from (1) but is paid from (2) — users see one number and receive another (see FL-7 for the client side). Fix: one source of truth (system_configs), remove the per-row amounts or make the engine read them.
- DR-1 [Low] `adRewardCoin.storeAdReward` limits rows with `totalAdReward >= settingJSON.maxAdPerDay`; `maxAdPerDay` is also the daily ad cap in other code, so raising the cap to 25 allows 25 ad rows and lowering it below the number of existing rows blocks adding but not paying. `dailyRewardCoin.storeDailyReward` rejects `dailyRewardCoin: 0` and an admin can delete any of the 7 days, which makes the app's "Daily reward configuration missing" state reachable by admin action (no guard: all 7 days must exist).

## Admin forms [S]
- PP-1 [Low] `premiumPlan.update` calls `req.body.planBenefit.toString()` without a null check → TypeError/500 if the field is omitted; `amount`/`validity` are stored as received (no numeric validation, no positive check); `destroy` deletes a plan that users currently hold (history snapshots protect the history list but not the entitlement logic that reads the plan id). `getpremiumPlanHistory`/`fetchPremiumPlanRecords` use the date-range filters that return no rows (DT-1).
- CUR-1 [Low] Currency admin: the default can be changed to any currency and is copied to `settings.currency` (app symbol/code), but the Flutter UI formats money with a hard-coded `₹`/INR (`MoneyFormat.inr`) and Razorpay orders are INR-only, so selecting another default produces mismatched labels; `destroy` can delete the default currency; `defaultCurrency` updates documents in a non-atomic loop.
- ADV-1 [Info] Advertise admin stores AdMob unit ids and IMA tag URLs that are served to every client through `client/setting` (public by design). `store` creates a record containing only the Android interstitial field; `update` ignores empty strings (cannot clear an id).

## Live streaming
- LIVE-1 [Medium, suspected — needs Zego-enabled settings to reproduce] `POST client/liveUser/generateZegoAuthToken` issues a Zego token04 with **login + publish privileges for any `roomId` the caller names** (`liveUser.controller.js:307-318`, `stream_id_list: []`). The route only checks the caller's identity, not that the room is the caller's own live session (`user.channel` / `liveHistoryId`), so an authenticated user can obtain a token that lets them publish into another creator's room. Fix: derive the room from the caller's live session, grant publish only for it and viewer-only (privilege 1) otherwise.
- LIVE-2 [High if Live is offered on the Vercel deployment; CONFIRMED statically] Live state is cleaned up only through Socket.IO events: `socket.js` (`endLiveUser`, `disconnect`) is the only code that sets `users.isLive = false` / deletes `liveUsers`, and it is attached only in `functions/backend/server.js:89`. The Vercel entry (`api/index.js`) and the Cloud Functions entry do not create a Socket.IO server (Vercel functions cannot hold websockets). On the deployed API a user who starts a live session (`client/liveUser/live` sets `isLive: true`) can never end it: subsequent attempts answer "You are already live on another device", the user stays in `getliveUserList` forever, and live chat / view counters (`addView`, `liveChat`) do not exist. The Flutter app's `socket_manager_controller.dart` connects to the API base URL and would fail. The mobile live screens are present in the app (Zego has no web implementation, so web is unaffected). Verification suggestion: start a live session on the deployed API with a test account and check `isLive`; not done here (no production writes).
- LIVE-3 [Low] `liveUser` returns the success response and only then sends FCM `sendMulticast` to subscribers; on Vercel the work after the response is not guaranteed to run (PLAT-1). `getliveUserList` uses `$lookup … let/pipeline` (no `localField`), which crashes the shim (SM-1 class) — the live list is expected to return 500 (not run).

## Platform behaviour
- PLAT-1 [High, suspected — cannot be reproduced on a long-running local server] The code repeatedly **responds first and works afterwards**: `createWatchHistory` ("Early response" at `watchHistory.controller.js:88`, then the creator-earning writes), `deleteVideoReport` (`res.status(200)…` then storage/DB deletes, `report.controller.js:180-217`), `liveUser` FCM notifications. On Vercel Node functions the instance can be frozen as soon as the response is sent unless `waitUntil`/`after` is used (none is used: grep). Possible effects: a creator's earning is lost or applied late, deleted videos remain with a "successfully deleted" message, subscribers are not notified. Impact is intermittent and platform-dependent; to confirm, run these endpoints on a preview deployment and verify the post-response writes. Fix: do the work before responding, or use `waitUntil`.
- FIN-1 [Low] Legacy `createWithdrawRequest` deletes the user's earlier **declined** request when a new request is made (`withDrawalRequest.controller.js:251-253`), so the declined request and its reason disappear from the user's history and from admin "Declined" lists — an audit-trail loss on a money flow (the ledger collections keep the movement, the request record does not).
- PL-04 [Info] `newPlayList` accepts any `channelId` that exists (not necessarily the caller's own channel) but listing is keyed by `userId`, so this cannot place a playlist on another creator's channel (checked while analysing PL-02).
