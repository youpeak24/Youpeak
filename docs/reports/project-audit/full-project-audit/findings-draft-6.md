# Findings draft part 6 (rewards, creator earnings, history, feeds) — emulator evidence logs/audit-06-rewards.txt

- RW-1 [High, CONFIRMED RW-01] Daily like cap/earning cap bypass: `reverseReward` (rewardEngine.js:472-513) decrements `dailyLikesToday` and `dailyEarningCoinsToday` when a like is removed but only claws back `min(amount, balance)`; a user who converts the 2 coins to withdrawable ₹ (`coinToAmountConverter`, no minimum — `minConvertCoin` is displayed but not enforced) between like and unlike keeps the money and the counters reset. 7 cycles produced 14 coins (cap = 5 likes = 10 coins); each cycle only waits the 3 s pacing gap, so the Free tier ₹10/day cap is bypassable (≈₹500+/day per account at 1 cycle/3 s), also for dislikes. Fix: ledger-based reversal that blocks conversion of unsettled engagement coins or never decrements the daily counters.
- WH-1 [Critical, CONFIRMED RW-02] `POST client/watchHistory/createWatchHistory` (watchHistory.controller.js:16-202): the per-(viewer,video) dedupe row is written with `WatchHistory.updateOne(..., {upsert:true})`, but `Model.updateOne` ignores `upsert` (mongooseShim.js:776-789) so the row is never created (watch-history rows stored = 0). Every call therefore passes the "already credited" test and credits the creator `watchTime/3600 × earningPerHour` again: 5 identical calls credited ₹10 for one 1-hour video; the creator's `totalEarningAmount` is directly withdrawable. Any second account of the creator can mint earnings without limit; `currentWatchTime` is also client-supplied. The handler additionally sends HTTP 200 before doing the writes (lost on Vercel freeze).
- WH-2 [High, CONFIRMED RW-03] `syncPlayback` (playbackSession.controller.js:13-55): `findOneAndUpdate(..., {upsert:true})` creates a document without the query keys (D-05) and ignores `$setOnInsert`; 3 syncs stored 3 rows with no `userId`, and `getMyWatchHistory` returned nothing → "continue watching"/history is empty and every heartbeat adds an orphan document (unbounded growth/cost).
- WH-3 [Medium] `weeklyViewsAnalytics` uses `$dateToString` (shim returns null) and a Date-vs-ISO-string range → creator view analytics are empty/grouped under null.
- CM-1 [High, CONFIRMED RW-04] `GET client/videoComment/getComments` (and `repliesOfVideoComment`) answer HTTP 500 "Cannot read properties of undefined (reading 'indexOf')": the shim's `$lookup` implementation (mongooseShim.js:230-243) requires `localField`/`foreignField` and cannot execute the `let` + `$expr` pipelines these handlers use. The comment list of a video cannot be loaded. Check: other handlers using `let/$expr` lookups — watchHistory.getWatchHistory (225-286), playbackSession, saveToWatchLater, userWiseDownload.
- FEED-1 [Medium, CONFIRMED RW-05] Home feed `type=all` is "seeded random" via `$toLong($toDate($_id))`; the shim returns 0 for string ids so the sort key is constant and the feed is ordered by ascending `_id` — oldest videos first for every user and every seed.
- FEED-2 [Medium, CONFIRMED RW-06 by source] `type=popular` sorts by the `views` lookup array before `$size` (video.controller.js:1903, 2093) → ordering is meaningless; and views are always 0 due to CF-01.
- PERF-1 [High/scale] Every feed/search call runs `Video.aggregate` which loads the whole `videos` collection plus whole `$lookup` collections (users, watch histories, subscriptions, unlocks, comments, likes, watch-later) into memory (mongooseShim.js:856-870), 25+ pipelines. Firestore billing and latency grow linearly with total data per request; the 8 s per-operation timeout and Vercel 30 s limit will be hit as data grows.
