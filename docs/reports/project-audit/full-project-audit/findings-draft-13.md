# Findings draft part 13 — payment recovery and Flutter client reliability

## PAY-5 [High, CONFIRMED by code read] A paid order is silently abandoned if the screen is closed or the app is killed before `verify`
- Evidence:
  - `features/coins/widget/coin_payment_view.dart:84-104`, `features/premium/view/payments_view.dart:79-96`, `features/video_promotion/view/promote_video_view.dart:~175` all do: `onSuccess: (response) async { if (!mounted) return; … PaymentApi.verify(orderId, paymentId, signature) … }`.
  - `dispose()` calls `_razorPayService.dispose()` which `clear()`s the Razorpay listeners, so a success event that arrives after the user navigated back (or after Android re-created the activity while a UPI app was in the foreground) never reaches `verify`.
  - The client never calls `client/payment/status` (`Constant.paymentStatus` is defined but unused — grep), stores no pending order id, and does not re-verify on next launch.
  - Production has no Razorpay webhook secret (DEP-4: `no_webhook_secret`), so the server cannot fulfil from the gateway callback either; the only repair path is the admin payment reconcile API, which has no UI (AFE-17).
- Impact: a user can be charged (₹ for coins, premium or a video promotion) and receive nothing, with no automatic recovery and no visible error. Highest likelihood on Android UPI flows and on web when the tab is closed or the popup callback is lost.
- Fix: persist `{orderId}` at `createOrder`; on success call `verify` even when unmounted (move the call out of the widget into a service); on app start and on the payments screens call `payment/status` for pending orders; configure the webhook secret (DEP-4) so the server fulfils independently; add an admin reconcile screen. Test: Flutter widget test that disposes the view between `createOrder` and the SDK success callback and asserts `verify` is still called; backend test that a signed `payment.captured` webhook fulfils an order that was never verified (suite 04 covers the server half in the emulator).

## PROMO-2 [High, product/consumer protection] Video promotion is sold in the app but never delivered
Combines PROMO-1 (backend has no ad-delivery/impression mechanism — nothing reads `videoPromotions` when building feeds) with the app UI that shows a plan name, a price and an "impression range" per plan (`_kPlanImpressionRanges`, `promote_video_view.dart`). Users pay real money via Razorpay for a promised reach that no code produces. Until delivery exists, the purchase entry should be hidden or the copy changed.

## FL-18 [Medium] 101 of 104 HTTP calls in the Flutter app have no timeout
`grep -rnE "http\.(get|post|patch|put|delete)\(" youpeak/lib` finds 104 calls; only `AppApiClient` (15 s) and the R2 PUT (15 min) bound the wait. Every legacy `*_api.dart` (feeds, profile, wallet, comments, subscriptions, …) awaits a bare `http.get/post`. On a stalled mobile connection (TCP established, no response — common on 2G/captive Wi-Fi) the loader never resolves, the user has no retry, and Get dialogs opened with `barrierDismissible:false` (`Get.dialog(LoaderUi…)`) stay on screen. Fix: wrap in a shared client with timeout and map failures to an error state with Retry.

## FL-19 [Medium] Video upload reads the whole file into memory and uses a single PUT
`core/file_upload/direct_upload_video_api.dart:41-46`: `LocalMedia.readBytes(videoPath)` then `http.put(... body: fileBytes).timeout(15 min)`. A 300 MB–2 GB phone video is held fully in RAM (Dart heap / browser memory) — expect OOM on low-end phones and in the browser; no progress callback (the upload screen cannot show progress), no resumable/multipart upload, no retry, and a 15-minute hard timeout aborts slow uploads at the end (the object is orphaned in R2: ME-1). The server enforces no maximum size on the presigned PUT (ME-2) while the client has none either. The legacy `ConvertVideoImageApi` (thumbnails) still goes through the 4.5 MB-capped serverless function. Fix: stream the file (`http.StreamedRequest`) or R2 multipart upload with progress, add a client size cap and server-side `Content-Length` condition.

## FL-20 [Low] Referral screen shows a legacy number and a hard-coded "1"
`referral_program_view.dart:127-159` displays the literal "1 member → `referralRewardCoins` coins" (`WithdrawSettingApi...referralRewardCoins ?? 0`), which is the legacy per-user referral setting, not the V9 partner/Tasker workflow (Milestone 1 / Milestone 2 reward coins from `partner_program`). The reward the user sees therefore does not match the rules the engine applies (RF-1..RF-5), and shows `0` when the settings call failed. The screen also prints the referral link to the console (`print("******* ${AppSettings.referralCodeLink}")`).

## FL-21 [Info, GOOD] Peak Boost client
`peak_boost_bottom_sheet.dart`: unique `requestId` per attempt, reused after a network failure so a retry cannot double-charge, regenerated after any definite refusal; amount validated against `minCoins`/`maxCoins`; semantics labels on cards and balance; disabled button while submitting. Server-side idempotency is asserted by the repository's own emulator suite (`tests/emulator/suites/04-peakboost.cjs`, check PB-04: same requestId replayed returns the first result and charges once; part of the 115/115 passing run). My audit suites did not re-test Peak Boost.
